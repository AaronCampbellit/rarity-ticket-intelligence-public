# Entity Contracts

**Status:** Detailed draft\
**Version:** 0.1\
**Last updated:** 2026-07-25

## Purpose

This specification defines the common contract every first-class Rarity entity must satisfy. It turns the architecture manifesto’s “everything is an object” principle into implementable requirements.

## Common envelope

Every entity carries:

| Field | Requirement |
|---|---|
| `id` | Immutable UUID generated by the platform |
| `object_type` | Stable, versioned canonical type |
| `msp_id` | Required installation/MSP scope |
| `client_id` | Required for client-bound objects; absent only for explicitly MSP-global types |
| `display_id` | Optional human-readable identifier, separate from the UUID |
| `lifecycle_state` | Active, inactive, archived, deleted, or type-specific governed state |
| `version` | Monotonically increasing optimistic-concurrency value |
| `created_at`, `created_by` | Immutable creation metadata |
| `updated_at`, `updated_by` | Latest accepted mutation metadata |
| `deleted_at`, `deleted_by` | Tombstone metadata when soft-deleted |
| `metadata` | Bounded, schema-governed extension metadata |

The API never trusts a caller-provided MSP or client scope. Scope is derived from the authenticated principal and authorized parent relationship, then checked against every referenced object.

## Entity families

### MSP-global

Organization settings, technicians, departments, teams, selected queues, global workflows, global automations, integration definitions, identity providers, platform roles, and platform health objects may be MSP-global. Their APIs still require explicit MSP scope and capabilities.

### Client-bound

Clients, locations, contacts, client queues, work records, assets, services, contracts, client knowledge, opportunities for existing clients, proposals, projects, phases, change orders, tasks, comments, attachments, time entries, and graph edges are client-bound. Prospects and their opportunities may remain MSP-scoped until conversion, but every access path must still enforce explicit prospect authorization. A relationship between two client-bound objects requires matching `client_id` unless an explicitly reviewed cross-scope relationship type permits otherwise.

### Derived

Search projections, reporting projections, caches, presence, correlation suggestions, and AI recommendations are derived objects. They retain source IDs and scope, are rebuildable, and never become the authoritative business record.

## Mutation contract

Every mutation follows this order:

1. Authenticate the principal and establish trusted request context.
2. Resolve MSP and client scope from trusted state.
3. Authorize the capability against object, scope, relationship, and workflow state.
4. Validate schema, field policy, referenced objects, and domain invariants.
5. Enforce concurrency with the current entity version.
6. Write business state, audit data, and event-outbox records atomically.
7. Return the accepted representation, new version, and correlation ID.

Side effects such as email, webhooks, search indexing, and automation occur from durable events after the transaction commits.

## Version and history

Material field and relationship changes create history records with the actor, source, reason where supplied, previous values, accepted values, correlation, and causation. Secrets and sensitive payloads use schema-defined redaction. Published workflow, automation, form, role, and schema versions are immutable.

## Custom fields

Custom fields must declare:

- stable key and display label;
- data type and validation constraints;
- object types and record types where allowed;
- required/default behavior;
- search, filter, reporting, audit, and export policy;
- read/write capability overrides;
- client-visible classification;
- retention and sensitivity classification;
- schema version and migration behavior.

Custom fields cannot redefine identity, ownership, client scope, lifecycle, workflow version, audit, or other platform invariants.

## Deletion and restoration

Deletion defaults to a tombstone. The platform previews blocked dependencies and cascade effects. Restoration retains the original UUID, history, and relationships when valid. Permanent erasure is a separate policy-controlled action requiring explicit capability, retention eligibility, audit, and confirmation.

## Acceptance tests

Every new entity type must prove:

- client-scope enforcement on create, read, update, relationship, search, export, and deletion;
- capability enforcement for UI, API, automation, and background-job callers;
- optimistic-concurrency conflict behavior;
- audit and event completeness;
- safe soft deletion and restoration;
- pagination, filtering, and search behavior;
- schema migration and backward compatibility;
- bounded serialization and sensitive-field redaction.
